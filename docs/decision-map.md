# Карта решений Calls Calendar

Консолидированные решения о продукте **Calls Calendar**. Единственный источник истины для домена, поведения и контракта API. Из неё сконструирована спецификация (issue #19) и вертикальные тикеты (#20–#26); она же ссылается на глоссарий `GLOSSARY.md` и ADR. Утверждается подтверждением владельца продукта в чате.

## 1. Что строим

Сервис записи на встречи: Владелец создаёт Типы событий и задаёт Рабочие часы; Гость выбирает Тип события и свободный Слот в окне «сегодня + 13 дней» и записывается; Запись становится Встречей. Две роли, без регистрации и авторизации.

## 2. Доменная модель

Термины закреплены в `GLOSSARY.md` (решение #8):

- **Владелец** — единственный заранее заданный профиль календаря; создаёт Типы событий и проводит встречи; без входа.
- **Гость** — тот, кто создаёт Запись; без аккаунта и без входа.
- **Тип события** — то, что владелец предлагает: название, описание, длительность (15–120 мин, шаг 15), формат (онлайн/оффлайн); `id` генерирует система.
- **Рабочие часы** — расписание доступности владельца по дням недели (начало/конец, пусто = выходной); ограничивает формирование Слотов (#9).
- **Слот** — предложение свободного времени: интервал `[начало, начало + длительность)`.
- **Запись** — процесс записи гостя (выбор Типа события и свободного Слота); несёт имя гостя.
- **Встреча** — подтверждённая запись: гость + Тип события (снимок) + занятый слот (время).

## 3. Семантика времени и слота (#10)

- Длительность слота = длительность выбранного Типа события (жёсткое свойство типа).
- Слоты на 15-минутной сетке; интервал целиком внутри Рабочих часов дня и окна.
- Окно: скользящее «сегодня + 13 дней».
- Занятость: интервалы не пересекаются; back-to-back разрешён; единая ось времени владельца независимо от Типа события.
- Таймзона: канонически **Europe/Moscow**; моменты — ISO 8601 со смещением; `dayjs` + плагин `timezone`. Гостю время показывается в локальной таймзоне браузера.

## 4. Поверхность владельца (#9)

- Слоты вручную не управляются: доступность выводится из Рабочих часов + окна + занятости.
- Три действия владельца: CRUD Типов событий; настройка Рабочих часов по дням недели; единый список предстоящих Встреч (только просмотр).
- Доступ без входа (единственный предзаданный профиль); конкретные маршруты — деталь интерфейса.

## 5. Сценарий записи гостя (#11)

1. Гость видит список Типов событий (название, описание, длительность, формат).
2. Выбирает Тип события.
3. Выбирает дату и свободный момент начала (15-мин сетка; занятые скрыты; при смене типа сетка пересчитывается).
4. Вводит имя (обязательно) и email (опционально).
5. Подтверждает.

- Атомарность: интервал занимает один гость; при гонке/повторной отправке — 409 и выбор заново.
- После подтверждения создана Встреча; email-уведомления, добавление в календарь, ссылки — вне скоупа.

## 6. Контракт API (#12)

HTTP + JSON, REST-подобно. Время — ISO 8601 со смещением (канонически Europe/Moscow); длительность — целое число минут; `id` — строка (UUID). Ошибки: 400 — валидация; 404 — не найдено; 409 — конфликт занятости; 500 — ошибка сервера.

| Метод  | Путь                             | Кто             | Назначение                                     |
| ------ | -------------------------------- | --------------- | ---------------------------------------------- |
| GET    | `/event-types`                   | гость, владелец | список Типов событий                           |
| POST   | `/event-types`                   | владелец        | создать Тип события                            |
| GET    | `/event-types/{id}`              | —               | деталь Типа события                            |
| PATCH  | `/event-types/{id}`              | владелец        | изменить Тип события                           |
| DELETE | `/event-types/{id}`              | владелец        | удалить Тип события                            |
| GET    | `/working-hours`                 | —               | текущие Рабочие часы (7 дней)                  |
| PUT    | `/working-hours`                 | владелец        | задать Рабочие часы                            |
| GET    | `/availability?eventTypeId={id}` | гость           | свободные моменты начала (окно 14 дней)        |
| POST   | `/bookings`                      | гость           | создать Запись → 201 Встреча / 400 / 404 / 409 |
| GET    | `/bookings`                      | владелец        | предстоящие Встречи                            |

## 7. Поведение сервера (#14)

- Доступность = 15-мин сетка × Рабочие часы × окно, минус занятые Встречи; только будущие моменты; интервал целиком в рабочем дне.
- `POST /bookings` атомарен: `eventTypeId` не найден → 404; валидация (пустое имя, время вне сетки/окна/рабочих часов, некорректный email) → 400; пересечение интервала → 409; успех → 201.
- Повторная отправка (двойной клик) → 409.
- Время нормализуется к Europe/Moscow.

## 8. Модель хранения (#15)

- **Тип события** — `{ id, название, описание, длительностьMinutes, формат }`.
- **Рабочие часы** — одна запись владельца: 7 дней `{ начало, конец }`, пусто = выходной.
- **Встреча** — `{ id, тип события: id + снимок (название, длительность, формат), начало, имя гостя, email? }`; конец = начало + длительность (не хранится).
- Снимок защищает историю: изменение/удаление Типа события не трогает существующие Встречи; удаление типа разрешено.

## 9. Декомпозиция (#16)

Вертикальный тикет = срез одной capability сквозь слои **контракт + сервер + интерфейс + тесты**; готов, когда реализованы и независимо проверены все четыре слоя; каждый объявляет свои блокировки. Карта решений фиксирует решения и критерий, но не режет конкретные тикеты и не пишет спецификацию — это отдельный шаг.

## 10. Машинный контракт (#17, #18)

- Источник истины — **TypeSpec** (`spec/main.tsp`): полный контракт из #12.
- Генерация одной командой `npm run spec:all`: OpenAPI (`spec/openapi.yaml`, эмиттер `@typespec/openapi3`), типизированный TypeScript-клиент (`src/api-client`, heyapi), серверные заготовки Fastify (`server/generated`: типы, JSON-Schema-валидация, стабы маршрутов).
- SDK подключён во фронте через обёртку API-клиента (`baseUrl` `/api` под Vite-прокси).

## 11. Вне скоупа карты решений

- Реализация кода (сервера и фронта) — отдельный шаг после карты (спецификация #19 и тикеты #20–#26 уже выпущены).
- Аутентификация и регистрация.
- Отмена и перенос Встречи (v1 = «только запись», #13).
- Email-уведомления, напоминания, добавление в календарь, ссылки на онлайн-встречу.
- Выбор технологического стека сервера.
