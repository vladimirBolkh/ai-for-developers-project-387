# План развития Calls Calendar

Дорожная карта развития продукта. Дополняет [карту решений](decision-map.md) и не отменяет её: всё, что противоречит текущей карте, помечено явно. Термины — по `GLOSSARY.md`.

Статус: **черновик на согласование**. Порядок этапов — рекомендуемый; внутри этапа задачи можно переупорядочивать.

## Контекст

Сейчас (v1.2) работает:

- SPA (Vite + React + Mantine 9) и in-memory бэкенд (`server/store.ts`) — данные теряются при каждом редеплое Render;
- контракт API в TypeSpec (`spec/main.tsp`) с генерацией клиента и серверных заготовок (`npm run spec:all`);
- две роли без аккаунтов: **Владелец** (единственный предзаданный профиль, без входа) и **Гость** (без аккаунта);
- CI-гейт: lint → format:check → test → build.

План переводит в скоуп три вещи, которые карта решений пока держит вне его (§11 «Вне скоупа карты решений»): **постоянное хранение данных**, **регистрацию и аутентификацию**, **пользователей с типами**.

> ⚠️ **Конфликт с картой решений**: §1 «Две роли, без регистрации и авторизации» и §11 «Аутентификация и регистрация» устареют после утверждения плана. Карту нужно обновить отдельным решением владельца продукта.

## Принципы

- **Вертикальные срезы**: каждый этап — сквозная capability (контракт → сервер → интерфейс → тесты), а не горизонтальные слои.
- **Контракт раньше кода**: изменения API сначала в TypeSpec, затем `npm run spec:all`, ручных правок сгенерированного кода не переживают регенерацию (`server/handlers.ts`, `server/store.ts`).
- **Готово = CI зелёный**: lint → format:check → test → build на каждом этапе.
- **Новые доменные термины в `GLOSSARY.md`** до того, как они попадут в код или тикеты.

## Этап 1. Полноценная база данных

**Цель**: данные переживают рестарт и редеплой сервиса.

Задачи:

1. **СУБД**: PostgreSQL (у Render есть бесплатный Postgres в том же регионе, что и сервис — Frankfurt). Альтернативы (SQLite, Key Value) рассматриваются только если бесплатный Postgres не подойдёт.
2. **Слой хранения**: выделить интерфейс репозитория поверх текущего `server/store.ts`, сделать реализацию на `pg` (параметризованные запросы, без ORM) и подключить её вместо in-memory стора. Dev-БД локально — через Docker (`docker compose up` с одним сервисом Postgres).
3. **Миграции и сиды**: версионированные SQL-миграции (напр. `node-pg-migrate`) + сид: дефолтный Владелец, пустые Рабочие часы. Миграции запускаются при старте сервера или отдельным скриптом.
4. **Конфигурация**: строка подключения через переменную окружения `DATABASE_URL`; в `.env.example` — локальный дефолт; в Render — привязать созданную БД.
5. **Тесты**: интеграционные тесты репозиториев на поднимаемой БД (или тестовый контейнер), плюс существующие тесты фронта остаются зелёными.

Критерии готовности:

- [ ] CRUD Типов событий, Рабочих часов и Встреч работает через PostgreSQL, in-memory стор больше не используется в проде.
- [ ] Данные переживают рестарт контейнера и редеплой Render.
- [ ] Локальный запуск: `docker compose up` + `npm run dev:all` поднимает рабочее окружение.
- [ ] Миграции идемпотентны, сид выполняется один раз.
- [ ] CI зелёный.

Блокировки: нет — этап первый.

## Этап 2. Регистрация новых пользователей

**Цель**: у учётных записей появляются вход и выход; данные защищены авторизацией.

Задачи:

1. **Учётная запись**: таблица `users` — `id`, `email` (уникальный, регистронезависимый), `passwordHash`, `name`, даты создания/обновления. Пароли — только хешем (argon2id либо bcrypt; выбор зафиксировать решением).
2. **Контракт (TypeSpec)**: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`; коды: 400 — валидация, 401 — нет входа/неверные данные, 409 — email занят. Затем `npm run spec:all`.
3. **Сессии**: серверный токен в httpOnly cookie + запись сессии в БД (проще и безопаснее, чем JWT в localStorage). Выход — инвалидация записи.
4. **Защита маршрутов**: существующие «владельческие» эндпоинты (CRUD Типов событий, PUT Рабочих часов, GET Встреч) начинают требовать вход; гостевые (список типов, доступность, запись) остаются открытыми.
5. **Фронт**: страницы «Регистрация» и «Вход», контекст авторизации (`/auth/me` при старте), guarded-маршруты, меню «вход/выход».
6. **Владелец**: решить, как мигрировать предзаданный профиль — предложение: при первой регистрации присваивать тип «Владелец», если учётных записей ещё нет; дальнейшие регистрации — по умолчанию без владельческих прав.

Критерии готовности:

- [ ] Регистрация → вход → выход → повторный вход работают; сессия переживает обновление страницы.
- [ ] Пароль не попадает в БД и в логи открытым видом; повторная регистрация на тот же email → 409.
- [ ] Владельческие эндпоинты без входа → 401; гостевой сценарий записи не сломан.
- [ ] CI зелёный.

Блокировки: этап 1 (нужна таблица `users` и хранилище сессий).

## Этап 3. Пользователи с разбиением по типам

**Цель**: у учётных записей есть тип, и сервер от него зависит.

Задачи:

1. **Типы пользователей** (предложение на утверждение владельцу продукта):
   - **Владелец** (`owner`) — управляет своим календарём: Типы событий, Рабочие часы, список Встреч;
   - **Администратор** (`admin`) — управляет учётными записями (список, смена типа, блокировка) и видит данные всех календарей для поддержки;
   - **Участник** (`member`) — обычный аккаунт: без управления календарём; в v1 доступны только вход и просмотр собственных данных.
     Точный состав типов и их права — продуктовое решение; перед реализацией зафиксировать в карте решений и, если появятся новые термины, в `GLOSSARY.md`.
2. **Хранение**: поле `type` (enum) в `users`; миграция существующих записей: первый пользователь → `owner`.
3. **Разграничение (RBAC)**: единая проверка типа на сервере для каждого защищённого эндпоинта (middleware/fastify-хук), 403 при нехватке прав; фронт прячет недоступные действия (это только UX, не защита).
4. **Контракт**: `GET /users`, `PATCH /users/{id}` (смена типа, админ) в TypeSpec + регенерация; фронт — страница управления пользователями для администратора.
5. **Смена типа**: админ меняет тип пользователя; аудит простого действия — лог на сервере.

Критерии готовности:

- [ ] Каждый защищённый эндпоинт проверяет тип; запрос «не своего» типа → 403.
- [ ] Администратор видит список пользователей и меняет типы; владелец — нет.
- [ ] Миграция назначила первого пользователя владельцем.
- [ ] CI зелёный.

Блокировки: этап 2 (нужны учётные записи и вход).

## Порядок и зависимости

| Этап | Блокируется | Результат                                              |
| ---- | ----------- | ------------------------------------------------------ |
| 1    | —           | PostgreSQL вместо in-memory, данные переживают рестарт |
| 2    | Этап 1      | Регистрация, вход/выход, защищённые маршруты           |
| 3    | Этап 2      | Типы пользователей и серверное разграничение прав      |

Каждый этап завершается обновлением `docs/decision-map.md` (и `GLOSSARY.md`, если появились термины) и, при необходимости, отдельным ADR в `docs/adr/` — например, выбор СУБД и механизма сессий.

## Вне плана (остаётся вне скоупа)

- Отмена и перенос Встречи (v1 = «только запись», #13).
- Email-уведомления, напоминания, добавление в календарь, ссылки на онлайн-встречу.
- Выбор иная серверного стека: остаётся Fastify + TypeSpec-генерация.

## Открытые вопросы

1. Типы пользователей и их права (этап 3) — утвердить владельцу продукта.
2. Как мигрировать предзаданный профиль Владельца после появления регистрации (этап 2, п. 6).
3. Механизм хеша паролей: argon2id vs bcrypt.
4. Бесплатный Postgres на Render: спящие базы и лимиты — проверить до старта этапа 1.
5. Обновить карту решений (§1, §11) после утверждения плана.
